# Figure Generation Standards

Every figure, table and diagram is generated by a script, and every one of them
is read by an assessor who will never open this repository. These rules govern
what the reader sees.

## Quick Reference

| Requirement | Rule | Detail |
|-------------|------|--------|
| Orientation | **Horizontal, always** | [Layout](#layout) |
| Box titles | Bold header row, plain body | [Typography](#typography) |
| Step numbers | Omit them | [Typography](#typography) |
| Contrast | Greyscale tiers, nested boxes lighter | [Contrast](#contrast) |
| Background | Transparent | [Contrast](#contrast) |
| Caption text | Submission-ready; no filenames | [Captions](#captions) |
| Internal notes | Separated, never in the caption | [Captions](#captions) |
| Values | Read from artefacts, never typed | [Provenance](#provenance) |
| Check | Look at the rendered file | [Verification](#verification) |

---

## Layout

**Prefer horizontal (landscape) layouts. The appendix prints landscape.**

A portrait figure wastes the page it is printed on and forces the reader to
rotate the document. Use `rankdir="LR"` for graphviz, wide aspect ratios for
matplotlib.

Target roughly **2:1 to 4:1** (width:height). A long linear pipeline may
legitimately reach 6:1 — what matters is whether each box stays readable at
landscape page width, not the ratio itself.

If a flow runs so wide that labels shrink below readable size, do **not** switch
to portrait. Instead, in this order:

- **shorten the labels** (usually the real fix),
- **group stages into clusters**, which shortens the row and adds structure,
- **narrow the caption wrap** — a wide caption sets a *floor* on figure width,
  so a long single-line caption silently stretches the drawing above it.

**Do not force rows with `rank="same"`.** Pinning ranks against the edge
direction fights the layout rather than steering it: attempts to wrap an
eight-stage LR flow into two rows produced a *column* (ratio 0.8) and a
staircase. Let graphviz assign ranks from the edges.

A figure that is unreadable at page width has not been delivered, but the fix is
a better horizontal arrangement, not a vertical one.

## Typography

**Bold the header line of every box; leave the body plain.** The header names
the thing, the body describes it, and the reader should be able to scan headers
alone. In graphviz this means an HTML-like label:

```python
def _box(title: str, *body: str) -> str:
    """Bold title over plain body lines."""
    rows = "".join(
        f'<TR><TD ALIGN="CENTER"><FONT POINT-SIZE="9">{l}</FONT></TD></TR>'
        for l in body)
    return (f'<<TABLE BORDER="0" CELLBORDER="0" CELLSPACING="0" CELLPADDING="1">'
            f'<TR><TD ALIGN="CENTER"><B>{title}</B></TD></TR>{rows}</TABLE>>')
```

**Do not number the stages** ("1 — Access", "2 — Aggregate"). The arrows already
carry the order; a number adds a second ordering system that can disagree with
the first, and it invites a reader to cite "step 4" — an internal name that means
nothing outside the repository.

## Contrast

Use a **greyscale tier system**, so nesting is visible without colour:

| Element | Fill | Why |
|---------|------|-----|
| Page background | `transparent` | the figure sits on whatever the document uses |
| Cluster / group box | `#ececec` | the container reads as a container |
| Node inside a cluster | `#fafafa` | nested boxes are *lighter* than their parent |
| Standalone node | `#f4f4f4` | between the two |
| Emphasis (the outcome) | white fill + accent border | draws the eye without shouting |

One accent colour only, and only on the element the figure is *about*. Everything
must survive greyscale printing, so never let colour be the sole carrier of
meaning.

Set `bgcolor="transparent"` on graphviz graphs and
`savefig(..., transparent=True)` on matplotlib figures.

## Captions

**Every caption is submission-ready prose.** Assume the reader has the thesis and
nothing else.

Never put in a caption:

- a script or filename (`run_preprocessing.py`, `metrics.csv`)
- an internal step number or pipeline stage name
- a plan ID, finding number, or decision code
- a repository path

Say **what the figure shows and what it means**, in the vocabulary of the thesis.

Internal notes — provenance, staleness flags, regeneration instructions, open
questions — go **below a horizontal rule under an `INTERNAL REVIEW` marker**, in
the accompanying `.md`, never in the caption or on the figure itself. A
screenshot cropped to the figure and its caption must be clean by construction.

This mirrors `export_appendix.py`'s existing `REVIEW_SEP` convention; reuse it
rather than inventing a second one.

## Provenance

**Every number is read from an artefact at render time. Nothing is typed into a
generator.** If a source table is missing, the generator exits with a message
naming the file rather than drawing a plausible figure from absent data.

Counts must be *counted*, not asserted: `len(list(dir.glob(...)))`, never a
literal `18` written from a directory listing that will be wrong next month.

Where a value genuinely cannot be derived (an editorial grouping, a design
rationale), state that boundary explicitly in the script's docstring and in the
review notes, and add a guard that warns when an item falls outside the curated
set.

## Verification

**Open the rendered file and look at it.** Generating without error is not the
same as rendering legibly. Every one of these was caught only by looking:

- a flow running ~1800px wide, unreadable at page width
- an orthogonal router driving edges *through* a cluster, leaving a node
  apparently unconnected
- a request/response figure placing the caller *below* the response it receives

Check: does it fit landscape at a readable size, do the headers stand out, is the
nesting visible in greyscale, does the caption stand alone without the repo?
